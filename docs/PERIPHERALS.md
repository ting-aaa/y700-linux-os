# TB320FC Debian peripheral bring-up

The November 19 checks used the PRC Y700 2023 running native Debian from internal UFS. They cover Bluetooth controller provisioning, discovery startup, the ALSA and PipeWire playback paths, and several signed-in desktop functions. The owner subsequently confirmed continuous sound during Chromium playback. Physical Bluetooth keyboard and mouse input and reconnect still require paired accessories. [Speaker playback](SPEAKERS.md)

## Bluetooth keyboards and mice

The original Debian kernel reported WCN6855 over Qualcomm UART, downloaded `qca/wcnhpbtfw21.tlv` and `qca/wcnhpnv21g.bin`, and completed UART setup. The board bundle contains both exact filenames. Debian 13 uses BlueZ 5.82 and Blueman 2.4.4. The PRC module tree includes UHID and HIDP. BlueZ 5.82 defaults to userspace HID and bonded-only Classic HID. [Asphalt firmware recipe](https://github.com/dianqk/nixos-android-devices/blob/8dcb481fc2ce91794fd294630e06f15a52ec7513/pkgs/asphalt/wifi-firmware.nix) · [BlueZ input defaults](https://github.com/bluez/bluez/blob/5.82/profiles/input/input.conf)

The WCN6855 Bluetooth controller needed its original public address before BlueZ could use it. Two independent Android records agreed on this tablet's address. The `y700-platform 0.1.0~dev5` service reads the address from the root-owned private file `/etc/y700/bluetooth-address` before BlueZ starts. It targets the Asphalt board's WCN6855 and sets the address only when the controller reports that the public address is missing. The installed unit was enabled and reported success. BlueZ reported the controller powered with the matching original address. An eight-second discovery run completed successfully.

The pinned NixOS port for the same tablet reports discovery and unpaired L2CAP traffic, unsuccessful pairing and a Bluetooth failure after one of two suspend/resume trials. Xiaomi Unicorn uses the same `qcom,wcn6855-bt` compatible and provides a comparable pre-BlueZ public-address service. [Asphalt status](https://github.com/dianqk/nixos-android-devices/blob/8dcb481fc2ce91794fd294630e06f15a52ec7513/docs/asphalt/status.md) · [Unicorn comparator](https://github.com/dianqk/nixos-android-devices/blob/17f4a785e2737d4635d2bf55369e519a635bde49/pkgs/mobile/bluetooth-identity.py)

Run `bash scripts/check-bluetooth-hid.sh` on the booted Debian system before and after connecting each peripheral through Blueman. It reports controller power, aggregate Classic HID and LE HID service counts, pairings, bonds, connections, resolved services and kernel keyboard/mouse event nodes. Only peers whose cached service UUIDs advertise HID contribute to the peer counts. A device advertising both profiles contributes to each profile count and once to the paired total if paired. An unavailable D-Bus inventory produces a separate status. The report omits device names, addresses and keystrokes. [BlueZ Device API](https://github.com/bluez/bluez/blob/5.82/doc/org.bluez.Device.rst) · [Private-bus inventory test](../tests/bluetooth-hid-inventory.sh)

Test a keyboard and mouse independently. Confirm harmless text input, pointer movement, buttons and scroll in Xfce. Power-cycle each peripheral, then check reconnect after a new session and after suspend once that system path is ready. Record the device type and transport with each result. Input nodes establish kernel enumeration. The interaction checks establish whether Xfce can use them.

The dev6 platform upgrade on the existing tablet preserved the boot and LightDM invocation. Its enabled Bluetooth identity unit succeeded, matched the original adapter address and left the controller powered. In one LE test BlueZ on the tablet received the random 16-byte payload advertised by the computer. In a second test BlueZ advertised a new payload and the computer's passive scanner received the exact bytes. Discovery ended and the tablet's active advertisement count returned to zero. No keyboard or mouse event nodes were present. Pairing, HID input and reconnect still require each type of peripheral.

After the dev7 rotation update, the real WCN6855 remained powered and `/dev/uhid` was present. The live BlueZ inventory succeeded and contained zero peers advertising either HID service, zero bonded or connected HID peers and zero Bluetooth keyboard or mouse event nodes.

### Prepare a fresh installation

The common image omits per-unit identities. Before switching a TB320FC to Debian, connect its stock Android system to an authorized ADB host. On a Linux host with `adb` on its PATH, select the tablet's serial and generate a private file. The tool makes one read-only shell call for the vendor model, vendor device, Lenovo adapter address and Android Bluetooth service address.

```sh
umask 077
uv run --no-project --python 3.13 python scripts/prepare-bluetooth-identity.py \
  --adb-serial "$ADB_SERIAL" --output "$PRIVATE_DIR/bluetooth-address"
```

If the tablet already runs Debian, replace `--adb-serial "$ADB_SERIAL"` with `--getprop "$PRIVATE_GETPROP"` to use a saved stock Android property listing from that same tablet. The property-only route requires TB320FC as both vendor model and device, plus agreement between `ro.odm.lenovo.btaddr` and `persist.vendor.service.bdroid.bdaddr`. A capture without both addresses can use `--android-config "$PRIVATE_ANDROID_CONFIG"` with the original `data/misc/bluedroid/bt_config.conf`. That route reads only the local `[Adapter]` identity. An additional `--getprop` can cross-check the Bluetooth service address. The output has mode 0600 on Linux and creation requires a new filename.

On the tested CN350 unit, the two stock properties agreed with Android's recorded `androidboot.btaddr` bootconfig entry in display order. An earlier stock capture also held the same Lenovo property. A fresh USB SSH connection compared the resulting private file with both the installed identity and the powered WCN6855 as reported by BlueZ. This validation used the saved Android records. The local hardware test covered the existing Debian controller. The current Debian device tree and boot arguments expose no Bluetooth address, and the tested internal persist filesystem lacks the Qualcomm `.bt_nv.bin` file. The original hardware storage for the value is unresolved. [Android boot property import](https://android.googlesource.com/platform/system/core/+/refs/tags/android-15.0.0_r1/init/property_service.cpp#1395) · [Qualcomm NV file definition](https://github.com/tadiphone-caf/vendor_qcom_proprietary/blob/9a79e3c6b709ced2c53befa46628395989d8892b/bluetooth/hidl_transport/bt/1.0/default/bt_nv.h#L35-L39)

On a fresh per-device installation, install that one file as `/etc/y700/bluetooth-address` with owner root and mode 0600. The enabled unit runs at BlueZ startup. After provisioning an already running tablet, start `y700-bluetooth-identity.service` and check controller power using `scripts/check-bluetooth-hid.sh`.

## Built-in speakers

The stock-derived board wiring has two CS35L45s. The PRC Debian kernel identified both as revision A0/OTP 0B. It also logged an ADSP AudioReach `APM_CMD_GET_SPF_STATE` timeout and a playback frontend with no enabled backend. Identify the actual enumerated card, its controls and the UCM result before changing topology or gain. A separate postmarketOS port for the Lenovo Q706F demonstrates the same amplifier's dependency on correctly named protection firmware. Its board wiring, speaker count and profile are specific to that tablet. [Asphalt sound and DSP device tree](https://github.com/dianqk/nixos-android-devices/blob/8dcb481fc2ce91794fd294630e06f15a52ec7513/pkgs/linux-kernel/sm8475/asphalt/patches/local/0008-asphalt-usb-audio.patch) · [AudioReach opcode definitions](https://github.com/torvalds/linux/blob/master/sound/soc/qcom/qdsp6/audioreach.h) · [Q706F observations](https://github.com/dasudiy/pmos-lenovo-q706f#4-audio-only-dummy-output)

Candidate 03 had the board's `Lenovo-Y700/HiFi.conf` but lacked ALSA's global `ucm2/ucm.conf`. The current Debian lock includes `alsa-ucm-conf 1.2.14-1`, authenticated against the retained Trixie index. On the running tablet, the global configuration and the card long-name alias `conf.d/sm8475/lenovo-LenovoLegionY7002ndgen.conf` together let `alsaucm -c hw:0 list _verbs` enumerate `HiFi`. The image builder supplies the same alias. [ALSA UCM entry point](https://github.com/alsa-project/alsa-ucm-conf/blob/v1.2.14/ucm2/ucm.conf) · [Asphalt HiFi configuration](https://github.com/dianqk/nixos-android-devices/blob/8dcb481fc2ce91794fd294630e06f15a52ec7513/pkgs/asphalt/HiFi.conf)

The owner confirmed sustained Chromium/YouTube audio at 40% desktop volume after loading each amplifier's factory calibration and using −12 dB digital gain. Raw 249 (−40 dB) had left ordinary speech inaudible, even though the multichannel PCM and speaker DSPs were running. The installed dev12 profile restored the working configuration after the desktop reopened the sound device. [Speaker evidence](SPEAKERS.md)

The shipped PRC device tree names `SPK1` at I²C address `0x30` as **Speaker Left** and `SPK2` at `0x31` as **Speaker Right**. The saved native boot journal enumerated both amplifiers. AudioReach carries two 48 kHz S16_LE channels over one Primary MI2S data line. On each amplifier the UCM routes both serial inputs (`ASP_RX1`, `ASP_RX2`) into its protection DSP and feeds its DAC from `DSP_TX1`. [Board wiring](https://github.com/dianqk/nixos-android-devices/blob/8dcb481fc2ce91794fd294630e06f15a52ec7513/pkgs/linux-kernel/sm8475/asphalt/patches/local/0008-asphalt-usb-audio.patch#L71-L146) · [AudioReach topology](https://github.com/dianqk/nixos-android-devices/blob/8dcb481fc2ce91794fd294630e06f15a52ec7513/pkgs/asphalt/audio/Lenovo-Y700.m4#L10-L24) · [UCM DSP routes](https://github.com/dianqk/nixos-android-devices/blob/8dcb481fc2ce91794fd294630e06f15a52ec7513/pkgs/asphalt/HiFi.conf#L25-L47)

The two factory coefficient files included in the board image match the extracted Android originals. They share one DSP firmware program. Their tuning metadata identifies the `CS35L45A Stereo Superset` signal chain and gives `deploy_group=left` for SPK1 and `deploy_group=right` for SPK2. Their DSP Y-memory coefficient blocks also differ. This establishes separate tuning for the two labeled outputs. The existing playback logs leave open how much of each input channel reaches each physical speaker. [Board firmware packaging](https://github.com/dianqk/nixos-android-devices/blob/8dcb481fc2ce91794fd294630e06f15a52ec7513/pkgs/asphalt/firmware.nix#L20-L24)

To check audible separation when a listener is present, use the protected speaker profile at its recorded setting and the private two-second 48 kHz fixture `.local/speaker-probe.wav`. It puts a low-level 440 Hz tone only in the left channel for the first second and only in the right for the second. Record the tablet's orientation, which grille is audible in each interval, and whether the sound switches sides. Check the journal for new DSP, DAI or protection faults. The three-second digital-silence test supplies a separate check of the two active PipeWire links. [PipeWire playback evidence](CAMERA-PIPEWIRE.md)

## Hardware and desktop interfaces

Android's BSP combines the vendor kernel and DT, vendor firmware/calibration, vendor daemons and Android HALs. On this native system, Debian talks to mainline-derived kernel interfaces directly. The board DT describes the UART, I²C/DSI, CCI/CSI, power supplies and audio links. BlueZ uses kernel HCI/HID, PipeWire and WirePlumber use ALSA/ASoC, and camera applications use V4L2/media-controller or libcamera. The sensor hub needs SLPI firmware, FastRPC and SSC before the desktop can consume orientation through `iio-sensor-proxy`. Shared chip names guide driver reuse. Firmware filenames, topology, calibration, GPIOs and rails come from the target board. [Asphalt hardware](https://github.com/dianqk/nixos-android-devices/blob/8dcb481fc2ce91794fd294630e06f15a52ec7513/docs/asphalt/hardware.md) · [Qualcomm FastRPC daemons](https://github.com/qualcomm/fastrpc/blob/development/Docs/daemons.md)

The original Debian boot already displayed the 1600×2560 panel, supported portrait and left-landscape touch, and carried HTTPS over the phone hotspot. The first temporary LightDM autologin on the original Debian kernel started Xfce and showed DSI-1 rotated left at 2560×1600, the registered NT36523N touchscreen, scale 1× and a 64-pixel panel. The display scale launcher opened a 526×153 window. Onboard had automatic display and docking enabled. Its D-Bus Show and Hide methods changed its visibility. The temporary configuration was removed and the normal authenticated greeter was verified active after that run. Physical touch in this trial and touch-only login remain unverified.

The same Xfce session showed Wi-Fi connected, one NetworkManager applet process and 11 access-point rows in the NetworkManager snapshot. On the shipped Xfce/X11 configuration, open the network icon in the panel and then its **Available networks** submenu. The primary tray event starts a scan and constructs the menu. The active access point appears above the submenu, and its remaining entries are deduplicated and sorted. **Network Connections** in Settings opens saved profiles, including when started with `nm-connection-editor --show --type wifi`. The actual menu listing, touch selection and reconnect on the tablet remain open. The Debian `network-manager-applet 1.36.0-3` source registers only the `enable-pref` GAction, and its application activation handler has an empty body. A second `nm-applet` invocation therefore supplies no menu-launch action. The optional Ayatana indicator exports its menu model to Xfce, whose notification-area plugin presents it from a panel button event. The `xfce4-panel 4.20.4-1` notification-area plugin supplies no remote-event handler to open a chosen item's menu. The versioned sources therefore provide no existing direct launcher for the applet's chooser from Settings or Applications. This is a source-level result from the exact Debian package versions.
