# TB320FC speaker comparison with stock Android

The TB320FC_PRC stock audio database and the Debian board agree on the speaker link. Both use the primary LPASS I²S interface, data line SD0, internally generated word select, two channels and 48 kHz S16 audio. The owner heard intermittent crackle and no usable program audio at the earlier −40 dB amplifier setting. The owner subsequently confirmed sustained, comfortable playback with factory calibration, a −12 dB amplifier setting and desktop volume at 40%. The register comparison below covers internal playback at the measured settings. Speaker limits, maximum volume and grille-by-grille stereo separation require independent evidence. [Speaker activation and tests](SPEAKERS.md)

## Factory signal path

The extracted CN350 `sku_cape/resourcemanager_waipio_mtp.xml` selects `MI2S-LPAIF-RX-PRIMARY` for `PAL_DEVICE_OUT_SPEAKER`. Its `sku_cape/mixer_paths_waipio_mtp.xml` selects slots 0 and 1 on both CS35L45s. Each local protection DSP receives ASP_RX1 and ASP_RX2, and its local DAC receives DSP_TX1. Both SoC and amplifier configurations use the same clock direction. The stock device tree assigns GPIO126 to bit clock, GPIO129 to word select, and GPIO127 to SD0. The Android pin group also contains GPIO128 for SD1. [Debian board topology](https://github.com/dianqk/nixos-android-devices/blob/8dcb481fc2ce91794fd294630e06f15a52ec7513/pkgs/asphalt/audio/Lenovo-Y700.m4) · [Asphalt board patch](https://github.com/dianqk/nixos-android-devices/blob/8dcb481fc2ce91794fd294630e06f15a52ec7513/pkgs/linux-kernel/sm8475/asphalt/patches/local/0008-asphalt-usb-audio.patch)

The stock `usecaseKvManager.xml` assigns the speaker device graph the key/value `a2000000:a2000001`. Following the ACDB graph lookup tables into the data pool gives subgraph `b0000002`. The tag lookup for that subgraph, tag `c0000004`, resolves both recorded selector values to module instance `428d` and parameter `08001019`. Both payloads decode to `(0, 0, 1, 1)` for LPASS, primary, SD0 and internally sourced word select. This identifies the speaker data line even though Android muxes two data pins. The ACDB lookup used the vendor file directly. [AudioReach graph lookup](https://github.com/AudioReach/audioreach-graphservices/blob/95230938e3bd32abb401ad54dd0d8f893d4210b6/acdb/src/acdb_data_proc.c) · [Tag and data-pool lookup](https://github.com/AudioReach/audioreach-graphservices/blob/95230938e3bd32abb401ad54dd0d8f893d4210b6/acdb/src/acdb_command.c) · [I²S parameter layout](https://github.com/AudioReach/audioreach-graphservices/blob/95230938e3bd32abb401ad54dd0d8f893d4210b6/spf/api/modules/i2s_api.h)

## Debian while the owner's stream was running

The physical pinctrl driver selected GPIO126/129/127 for SCK/WS/SD0. The primary MI2S bit clock had one prepare and one enable vote and reported 1,536,000 Hz, the rate for 48,000 frames/s × two 16-bit slots. Both CS35L45s reported the same configuration. ASP receive slots 0/1 were enabled, the receive slot and word widths were 16, and the amplifiers selected standard I²S with normal polarity. Both PLL configuration words selected the 1.536 MHz bit clock as their reference. Both DSPs reported booted/running and returned mailbox state 0 (running). Both DACs selected DSP_TX1. The active AudioReach frontend PGA reported its driver-default integer gain of 8192. Nonvolatile regmap configuration can come from the driver cache. A separate direct register read on both chips returned zero for the independent output-mute bit. [Codec driver](https://github.com/torvalds/linux/blob/194fcd20ebccbc34bba80d7d9b203920087bb01d/sound/soc/codecs/cs35l45.c) · [AudioReach gain default](https://github.com/torvalds/linux/blob/194fcd20ebccbc34bba80d7d9b203920087bb01d/sound/soc/qcom/qdsp6/audioreach.h)

| `0xe090` | `01401000` (bits 12, 22, 24) | Global enable asserted (22), power-up done (24). Amplifier short, boost short, boost undervoltage, thermal error and VBATT undervoltage fields were clear. |

These were reads of the volatile status bank. The interrupt driver uses a separate event/acknowledgement bank at `0xe010` and following. No event acknowledgement was issued. The public headers identify the listed fields. The other asserted bits in the table remain unidentified here. These snapshots and the absence of matching audio errors in the kernel journal do not measure earlier transients. A separate set of three running-stream samples returned `SPK_OUTPUT_POWER=0`, `VMON_LOW_FLAG=1`, `REDUCE_POWER=0` and `CSPL_ERRORNO=0` from both protection DSPs. The available firmware descriptors give no unit for that output-power value. ## Gain and amplifier controls

The factory Android kernel module's register-default table gives `0x00100000` for AMP_PCM_CONTROL (`0x7000`). Its signed low 11 bits encode 0 dB, equivalent to raw 409 on the Debian control. The stock mixer XML configures the 4 ms soft ramp in its own field. The XML does not set the digital gain. The speaker path requests +19 dB analog gain and clears the separate AMP Mute control. In the exact factory module this control points to register `0x7c04`, bit 0 and the generic `snd_soc_put_volsw` callback. The Android values describe the packaged defaults and setup path. A running Android register capture would be required to establish the eventual media-session gain. [Cirrus Android mixer implementation](https://android.googlesource.com/kernel/google-modules/amplifiers/+/refs/heads/android-msm-eos-android13-wear-kr3-pixel-watch/cs35l45/cs35l45.c) · [Cirrus Android register defaults](https://android.googlesource.com/kernel/google-modules/amplifiers/+/refs/heads/android-msm-eos-android13-wear-kr3-pixel-watch/cs35l45/cs35l45-tables.c)

The factory mixer enables the boost-converter brownout prevention engine (BBPE) and the inter-amplifier SYNC function. The factory module maps them to BLOCK_ENABLES2 (`0x201c`) bits 13 and 8. Both bits were clear on the tested Debian system. Both factory device-tree codec nodes select GPIO1 function 2 (MDSYNC), and both Debian codecs reported the same pad mux. The stock mixer specifies no SYNC leader. The shipped protection program exposes neither the MDSYNC algorithm `f20a` nor its `MASTER`/`NUM_DEVICES` control descriptors. The role-assignment procedure documented by a different Android Cirrus implementation depends on that algorithm. The factory labels for left and right identify audio tuning groups and supply no transmitter IDs. [Cirrus SYNC proposal](https://lore.kernel.org/r/20260828-sound-for-next-cs35l45-sync-v4-v5-0-fe3feba709ff@opensource.cirrus.com) · [Factory reference driver](https://android.googlesource.com/kernel/google-modules/amplifiers/+/refs/heads/android-msm-eos-android13-wear-kr3-pixel-watch/cs35l45/cs35l45.c)

Each factory DTBO amplifier node contains six four-cell `bst-bpe-inst-*` arrays. The exact Lenovo ARM64 module asks the OF parser for **at least five cells** in each array. Its probe loads 5 at text offset `0x2484`, calls `of_property_read_variable_u32_array` at `0x2494` and skips the entry on error at `0x2498`. Consequently this configuration path skips all six arrays. The stock register defaults give `0x5a46321e` for the four threshold fields, where reading the four-cell DT literally would imply `0x6e46321e`. Direct readback from both Debian amps showed `0x5a46321e`. Eleven of twelve BBPE words matched the factory module's register-default table. For the twelfth, both amplifiers reported `BST_BPE_MISC_CONFIG=0x00008000` at `0x3c20`; the factory module declares zero, while Cirrus' newer public driver proposal declares `0x00008000`. Bit 15 is the inductor-current release-mode selection. No BBPE, SYNC or threshold changes were applied in this investigation. The audible acceptance at the measured working level does not qualify higher output levels. [Cirrus BBPE description](https://lists.openwall.net/linux-kernel/2026/11/09/2848) · [Boost configuration and register defaults](https://lists.openwall.net/linux-kernel/2026/11/09/2864)
