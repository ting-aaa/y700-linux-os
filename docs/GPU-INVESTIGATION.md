Two shortcuts are rejected from the actual source:

- **Blindly disabling IFPC:** the inspected `0x07030001` A730 catalog entry has no `ADRENO_QUIRK_IFPC`; initialization already chooses `GMU_IDLE_STATE_ACTIVE`. This does not disable every power transition, but an IFPC-off patch is not an established change to this configuration.
- **Changing the live preemption parameter and declaring an A/B test:** ring count is selected during GPU initialization. Writing the variable on the running driver does not recreate those rings. This test requires a separate attended boot/module initialization plan, not an unattended sysfs write.

The Asphalt queue already contains five GMU sync-state patches. Do not reapply a similarly titled patch without checking the actual source. Upstream itself records an unexplained GMU timeout and partial GLES support in its [pinned hardware status](https://github.com/dianqk/nixos-android-devices/blob/8dcb481fc2ce91794fd294630e06f15a52ec7513/docs/asphalt/status.md); that is corroborating context, not this tablet's diagnosis.

## HFI vote timeout on the working Debian boot

The running kernel's ELF notes matched the saved baseline vmlinux notes byte for byte (build ID `8032f7452420cd7f36dc6bf0084ff34ed6d2f25f`). The GMU identified its firmware as 4.0.7. The filtered monotonic journal through uptime 33853.294085 s contains 26 frequency/bandwidth vote timeouts. Each was followed by an unexpected response with the same sequence number. The time between the **two kernel messages** ranged from 1.892 to 26.654 ms, with a median of 2.617 ms. The sequence wraps modulo 4095, so pairing uses adjacent records within one boot. The original logger omits the echoed command type and queue state. These timestamps cannot tell when the response entered DMA memory or establish a common cause with the earlier GPU_SET hang. [Per-event measurements and build receipt](research/hfi-vote-diagnostic.json)

The configured devfreq target calls the GMU frequency setter under its mutex. When suspended it caches the requested rate. On resume, after firmware/HFI startup and enabling the fault IRQ, the driver clears the cached frequency and sends an initial vote. Both active paths may send blocking HFI command 30. The driver writes the command, signals the GMU, then polls the MSGQ bit (nominal one-second timeout per attempt) **before** reading the response queue. The error path returns without draining the queue. A later transaction can therefore read the earlier echo. The new rate is cached before the send and the caller ignores the HFI return code, so the cached rate alone cannot prove that the GMU applied it. The separately enabled fault IRQ handler clears all bits it observed. A simultaneous MSGQ clear is a possibility to measure.

The inspected Linux 7.3.y HFI source matched the board's complete HFI file (SHA-256 `3a545bcb6baf2505384b5cfd2e32464e5b8de04686af51d77a00917bb7d5343d`). A pinned mainline comparison retained the same interrupt wait, ACK handling, vote submission and fault-IRQ logic. The five Asphalt sync-state patches address device/component integration. This comparison yielded no verified fix for the paired events. [Stable HFI source](https://github.com/gregkh/linux/blob/linux-7.3.y/drivers/gpu/drm/msm/adreno/a6xx_hfi.c) · [Pinned mainline source](https://github.com/torvalds/linux/tree/9206b22fb959f4a9cf1921f34aed0df1dcb1ab04/drivers/gpu/drm/msm/adreno)

### Android driver reuse and browser coverage

The stock PRC kernel and device tree identify Adreno 730v3, `qcom,kgsl-3d0` and the vendor `msm_kgsl.ko` module. The Android EGL and Vulkan properties select the Adreno implementation. Native Debian uses the Linux DRM/MSM kernel interface, Mesa Freedreno for OpenGL, and Turnip for Vulkan. The display controller drives scanout separately. The board port supplies the Adreno and DPU wiring, and the GPU firmware can still come from the matching CN350 set. The driver interface, desktop compositor and presentation path must be tested on the Debian stack. [Mesa Freedreno](https://docs.mesa3d.org/drivers/freedreno.html) · [DRM/MSM](https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/tree/drivers/gpu/drm/msm) · [Asphalt kernel patch series](https://github.com/dianqk/nixos-android-devices/blob/8dcb481fc2ce91794fd294630e06f15a52ec7513/pkgs/linux-kernel/sm8475/asphalt/series.nix)

The [Chromium WebGL probe](../tests/chromium-gpu.md) verifies shader output and requires the browser to identify the Adreno 730 and its Mesa driver. A Windows browser rendered 12 frames in each of two control runs. The probe rejected both the software renderer and an NVIDIA GPU. Chromium on the tablet still needs the corresponding browser result, matching DRM submissions and kernel log under the candidate boot.
