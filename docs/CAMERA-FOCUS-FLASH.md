# Camera focus and flash on TB320FC_PRC

The 2023 TB320FC has a 13 MP autofocus rear main camera, an 8 MP fixed-focus front camera, a 2 MP fixed-focus rear macro camera and one rear LED. The board maps these to HI1339, S5K4H7 and SC202CS. On 2026-11-19, `cam --list-controls` on the tablet's installed private libcamera reported only `Contrast` and `Gamma` for each camera. The current stack exposes neither autofocus nor flash. [Lenovo TB320FC PSREF](https://psref.lenovo.com/Product/Lenovo_Tablets/Legion_Tab) · [Debian capture evidence](CAMERA-SENSORS.md) · [Asphalt camera port](https://github.com/dianqk/nixos-android-devices/blob/8dcb481fc2ce91794fd294630e06f15a52ec7513/docs/asphalt/hardware.md#cameras)

## What the original board describes

The retained CN350 Android A-slot device tree was reconstructed from vendor DTB index 2 and overlay index 14, as recorded by the earlier Android boot. The merged artifact used here has SHA-256 `7359763f57ceea931c6881581fa13c35198f0cb905116e00fdd20ec00cd181d5`. The HI1339/PHY0 node references an actuator and `led_flash_rear`. The macro/PHY1 node references `led_flash_rear_aux` and has no actuator. The front/PHY2 node has neither link. Both rear flash nodes share the same flash, torch and switch sources under the PM8350C controller at `0xee00`. The two logical rear-camera routes do not establish which Android capture modes can fire the shared LED.

| Item | Stock CN350 DT | Upstream mapping and limits |
| --- | --- | --- |
| Controller and sources | `qcom,pm8350c-flash-led` at `0xee00`; both rear routes reference `flash_1`/`flash_2` and `torch_1`/`torch_2`, with zero-based `qcom,id` 1 and 2 | The existing `led-controller@ee00` binding can represent one LED child with one-based `led-sources` 2 and 3. The driver subtracts one before programming the channels. |
| Torch | 500 mA maximum in each referenced channel node | A ganged child's `led-max-microamp` is the total across both channels. Their stock declarations sum to 1,000,000 µA, which fits the schema numerically. The original HAL's working total and board limits still need verification. |
| Flash | 1,500 mA maximum per referenced channel, 1,280 ms timeout per channel, 12,500 µA current-step declaration | `flash-max-timeout-us` can represent 1,280,000 µs. The current declarations sum to 3,000,000 µA, above the upstream 2,000,000 µA ganged ceiling. The driver divides ganged current across the channels. Its ceiling is a controller limit, not a measured board limit. |
| Switch and strobe | Both rear routes select `led_switch_2`, with symmetry enabled and mask `0x0f`. The controller also describes a hardware strobe on PM8350C GPIO 1. | The `flash-source`/`torch-source` phandles select the two relevant outputs. Neither the stock switch nor its GPIO property has a direct field in the upstream schema. The driver supports a V4L2 external-strobe mode. Camera-to-PMIC timing and routing still need verification. |
| Thermal and fault handling | `qcom,thermal-derate-current = <200 500>` and three named PMIC fault/ramp interrupts | The upstream schema has no field for the stock thermal array. In the retained four-channel driver, the PMIC overtemperature states cap the total at 1,000 mA or 500 mA, and the driver reads fault status. Stock threshold definitions, ordering and policy remain unverified. The overlapping value 500 does not establish equivalent behavior. |

## Debian driver path

The locked Linux board DTB has SHA-256 `1fcd5dedc5cec0b03e6f666421aaec317d0db2203bf3371a408078ba427deb7d`. It contains the disabled PM8350C `led-controller@ee00` and has no camera `flash-leds` or `lens-focus` references. The retained baseline kernel config and the embedded config extracted from the locked GMU queue-fix `Image` both set `CONFIG_LEDS_QCOM_FLASH=m` and `CONFIG_LEDS_CLASS_FLASH=m`. The retained module tree contains both `.ko.zst` files. Both configs leave `CONFIG_V4L2_FLASH_LED_CLASS` unset, so the existing LED module cannot register the V4L2 flash subdevice. [Board component hashes](../config/board-components.sha256) · [Queue-fix kernel hashes](../config/gmu-queue-kernel.sha256) · [V4L2 flash class Kconfig](https://github.com/torvalds/linux/blob/master/drivers/media/v4l2-core/Kconfig)

The Asphalt sensor driver calls `v4l2_async_register_subdev_sensor()`, which parses the standard firmware-node links. `flash-leds` names the LED child of the PMIC controller, and `lens-focus` names the separate lens-controller node. These links allow the corresponding subdevices to bind through the media graph. Whether libcamera's simple pipeline and qcam expose usable flash and autofocus controls must be checked separately. [Media device binding](https://github.com/torvalds/linux/blob/master/Documentation/devicetree/bindings/media/video-interface-devices.yaml) · [V4L2 firmware-node handling](https://github.com/torvalds/linux/blob/master/drivers/media/v4l2-core/v4l2-fwnode.c) · [Asphalt wiring](https://github.com/dianqk/nixos-android-devices/blob/8dcb481fc2ce91794fd294630e06f15a52ec7513/pkgs/linux-kernel/sm8475/asphalt/patches/local/0016-asphalt-camera-wiring.patch)

### PC-only V4L2 bridge build

The [module builder](../scripts/build-camera-flash-bridge.sh) uses two jobs by default. It overlays the pinned compiled PRC tree inside a private Linux mount namespace, with the original tree mounted read-only. Run it on a host with OverlayFS, the baseline LLVM toolchain, AArch64 cross tools and `modinfo`.

```sh
mkdir -p out
sudo bash scripts/build-camera-flash-bridge.sh \
  /build/asphalt/linux-7.3.4 out/camera-flash-bridge
```

Kbuild's in-tree module targets build the bridge and its Qualcomm client together. The existing LED Flash class object is included in modpost so the generated dependency metadata names the real provider. The probe's functional config change is `CONFIG_V4L2_FLASH_LED_CLASS=m`. On this host `olddefconfig` also enabled `CONFIG_CC_CAN_LINK`, a generated userspace compiler probe used by the sample-program Kconfig. The script rejects other config differences. The original config, kernel Image, DTB and symbol table matched their original SHA-256 pins after the build.

Two independent overlays produced byte-identical AArch64 modules with the original `7.3.4-asphalt-prc SMP preempt mod_unload aarch64` vermagic. The bridge depends on `led-class-flash`. The Qualcomm module depends on both modules and imports the bridge's `v4l2_flash_init` and `v4l2_flash_release` exports. The symbol check found no unresolved imports against those module exports and the baseline table. `fdtget` still reported `disabled` for PM8350C `led-controller@ee00`. The two modules and the build, dependency and checksum receipts are in the ignored output directory. Module loading, LED output and camera controls remain untested for this build.

## Main-camera lens controller

The stock `cameraModuleData` identifies TXD, HI1339 and camera slot 0. It points to `gt9768_hi1339` and supplies no module-level address override. The separate `actuatorDriver` record at file offset `0x9efe` supplies the address, power and register settings. The CN350 `lib` and `lib64` copies of `com.qti.sensormodule.txd_hi1339.bin` both have SHA-256 `34ba25820a0ac983acd57075d8be57cb1b6eba55c3d315f5f7475c946149a3a8`. The narrow decoder follows typed references in this packed Parameter Parser V3.5.1 file and checks the camera-module link before reporting the actuator. It reads the existing local file and emits only selected fields. [Decoder](../scripts/decode-camera-focus.py)

| Item | CN350 configuration and source cross-check |
| --- | --- |
| Bus and address | The stock slot 0 sensor links to `asphalt_actuator` on CCI at `0x0ac15000`, master 0. CamX records write-address byte `0x18`. The SM8450 Qualcomm CCI path shifts that value right once, giving Linux address `0x0c`. CamX requests Fast-mode Plus, while the pinned native CCI master is configured for 400 kHz. The sensor already uses this bus at its own address `0x20`. |
| Supply | The actuator declares one `cam_vaf` consumer of PM8350C RPMh BOB `bobc1`, with 3,008,000–3,960,000 µV constraints and a 70,000 µA load request. Linux already describes the corresponding `vreg_bob` with the same bounds. The module requests VAF on with a 0 ms configured delay and off with a 1 ms configured delay. The DT bounds and load request give board configuration, while the actual voltage and any separately wired actuator logic supply remain unmeasured. |
| Chip identity and initialization | MediaTek's GT9768 submission checks byte register `0x00` for `0xe9`. CN350 has no explicit actuator ID override. Stock initialization writes `0x02 = 0x02`, `0x06 = 0x60` and `0x07 = 0x01`, each with a configured 100 µs delay. The register roles agree with the family control, AAC prescale and AAC timing registers. |
| Position | The stock operations describe a byte poll of `0x05` for zero with a 5,000 µs delay parameter, followed by a two-byte DAC write at `0x03` with no data shift. MediaTek's GT9768 implementation independently places DAC bits 9:8 in register `0x03` and bits 7:0 in `0x04` using a big-endian 16-bit write. The converter has 1,024 codes. |
| Nominal travel and ramp | The module gives initial DAC code 40, infinity and macro logical boundaries 0 and 400, one code per step and Q value 128. Both damping directions have a 400-step scenario limit, damping step-size field 511, delay 7,000 µs and hardware parameter zero. These are nominal settings. The module also references a TXD EEPROM, and usable optical endpoints and the HAL's runtime damping behavior still need verification. |
| Shutdown | The module's activate, standby, uninit and park lists are empty. It supplies the VAF-off power record. The stock HAL may issue extra motion outside this descriptor. MediaTek's submission walks to zero in steps of 16 with 1 ms sleeps during release. Neither that generic park sequence nor a sweep over the whole DAC range has been validated for this module. |

### TXD EEPROM focus calibration

The same stock module contains an `EEPROMDriverData` record at offset `0x9af8`. Slot 0 links to `txd_hi1339_eeprom`, with no module-level address override. Its read command uses CCI0 master 0, write-address byte `0xb0` (Linux address `0x58`), a 16-bit register address, byte data and 400 kHz. The shipped kernel's `cam_eeprom_update_i2c_info` shifts the address at `.text+0x140fb0` before storing the CCI SID at `.text+0x140fb4`. Android requests `0x1851` bytes from register `0x0000`. That window does not establish the EEPROM part or its full capacity. HI1339 in the pinned Linux device tree has no EEPROM node. [EEPROM schema](https://github.com/bjzhou/CamxChi/blob/9f17f1b568626b393e785b369c5dc94543774d7a/chi-cdk/api/sensor/camxeepromdriver.xsd#L912-L931) · [Board test](../tests/camera-focus-board.sh)

The stock HI1339 and EEPROM reuse the same power sequences. The stock DT shows shared GPIO122-controlled 1.8 V VIO, PM8350C L4, BOB VANA, MCLK0 and TLMM25 reset. The module's seven power-up records request reset asserted, VIO, custom L4, VANA, VDIG, 24 MHz MCLK0 and reset released. Delays are 1 ms after the first six records and 10 ms after reset release. The stock EEPROM node spells its VDIG property `am_vdig-supply`. The shared sequence and the declared supplies establish software requests. They leave the actuator's physical logic-supply wiring open. The actuator has a separate VAF request on BOB and the stock actuator node declares no VIO or enable GPIO. CamX creates and reads the EEPROM before constructing the actuator data and initializing its step table. EEPROM access has its own power-up and power-down command records. [CamX module initialization](https://github.com/bjzhou/CamxChi/blob/9f17f1b568626b393e785b369c5dc94543774d7a/camx/src/core/camximagesensormoduledata.cpp#L769-L817) · [CamX EEPROM power commands](https://github.com/bjzhou/CamxChi/blob/9f17f1b568626b393e785b369c5dc94543774d7a/camx/src/core/camxeepromdata.cpp#L375-L432)

For focus calibration, the narrow read window is 11 bytes at EEPROM offsets `0x27` through `0x31`. The module describes unsigned 16-bit big-endian words at infinity offset `0x28` and macro offset `0x2a`, each with mask `0xffff`. The shipped CN350 HAL applies two Asphalt-specific operations before using those words.

1. It computes CRC-16/UMTS over `0x27` through `0x2f` inclusive and compares the big-endian CRC at `0x30`–`0x31`. The polynomial is `0x8005`, with initial state and final XOR zero and no input or output reflection. The independent check string `123456789` gives `0xfee8`.
2. It right-shifts each 16-bit word by six. The top 10 bits are the factory DAC code. The low six bits have no role in this calculation. The module has no AF chart-distance table, Hall correction, orientation-specific endpoints or gravity correction configured.

The retained ARM64 `camera.qcom.so` has SHA-256 `92b130149f7f4b6ab0e57f8764b03df59b1ea0e657c6d438fbae056d5020370e`. It selects `FormatAFData_Asphalt_Rear` for `txd_hi1339_eeprom` at `0x11f8924`–`0x11f8938`. The same branch handles `ofilm_ov13b10_eeprom`. Both stock module variants use the same addresses and GT9768 actuator power sequence. The six retained sensor module files contain no second HI1339 actuator profile. A matching AF CRC verifies the block's integrity across either variant. The observed HI1339 sensor ID is the evidence specific to the TXD configuration. The AF path includes offset `0x27` in its CRC and does not use its value as a vendor identifier. [CamX integer reader](https://github.com/bjzhou/CamxChi/blob/9f17f1b568626b393e785b369c5dc94543774d7a/camx/src/core/camxeepromdata.cpp#L982-L1022) · [CRC parameter catalogue](https://reveng.sourceforge.io/crc-catalogue/16.htm#crc.cat.crc-16-umts)

The format dispatch calls the CRC helper at `0x1200330`. In isolated ARM64 emulation this helper accepted 66 synthetic matching CRCs and rejected the same cases with corrupt CRCs. The unsigned big-endian reader is at `0x12000e0` and the endpoint reductions are at `0x11f8a9c` and `0x11f8abc`. The later actuator calculation at `0x11b72d0`–`0x11b73dc` matches the CamX source. Each endpoint adds the truncated product of the absolute measured DAC span, its configured margin, and the sign of its original code (positive code gives +1, zero gives −1). TXD declares −0.20 at infinity and +0.20 at macro. The VCM clips adjusted infinity to at least zero and adjusted macro to at most 1023. The calibrated starting code is adjusted infinity and the code increment is the adjusted span divided by 400 steps. Three synthetic emulation cases agreed with the host parser on raw codes, margins and step increment, including clipping and the zero-infinity case. These calculations describe Android's table inputs. The unit's optical distance mapping, validated movement limits and park operation still need evidence. [CamX actuator calibration](https://github.com/bjzhou/CamxChi/blob/9f17f1b568626b393e785b369c5dc94543774d7a/camx/src/core/camxactuatordata.cpp#L66-L137)

```sh
uv run --no-project --python 3.13 python scripts/decode-camera-focus.py --eeprom-layout "$CN350_TXD_MODULE"
uv run --no-project --python 3.13 python tests/test_camera_focus_decoder.py
```

The command prints metadata from the stock descriptor. Host code can call `Module(stock_module_bytes).eeprom_layout()` and pass that metadata with an 11-byte window to `decode_af_block`. The parser checks the CRC, decodes the factory codes and reports the Android margin calculation. It rejects truncated, invalid and non-increasing codes. Only stock firmware metadata and synthetic calibration bytes were used to develop and test it. [Decoder and AF block parser](../scripts/decode-camera-focus.py) · [Synthetic regression](../tests/test_camera_focus_decoder.py)

The original native trial returned `ENXIO` before receiving any EEPROM bytes. On 2026-11-21 a separate counted kernel enabled WL2864C LDO5 during main-sensor runtime power. The fixed read at `0x58` then returned all 11 bytes. The factory CRC and unsigned, ordered 10-bit endpoints validated on the tablet. The measurement retained the pass/fail result and did not export per-unit values. [Physical measurements and power sequencing](CAMERA-FOCUS-PROBE.md)

## Physical Bring-Up Update (`hw-bringup-02` / `dev13.0`, 2026-11-22)

The unified `hw-bringup-02` kernel and `dev13.0` image enable all three camera sensors, the calibrated rear `GT9768` AF VCM actuator, and the conservative `PM8350C` rear LED flash/torch node (`config/kernel/asphalt-flash-led.dtsi`):

- **All 3 Camera Sensors (`libcamera v0.7.2` SoftISP)**: All three V4L2 subdevices (`sc202cs 2-0036` 2 MP macro, `hi1339 0-0020` 13 MP rear main, `s5k4h7 1-0010` 8 MP front) enumerated in `cam -l` and streamed 25 continuous frames each at ~30 fps (`7,641,600 B`, `52,416,000 B`, and `31,882,752 B` per frame respectively).
- **Rear AF Actuator (`gt9768 0-000c`, `/dev/v4l-subdev30`)**: Probed with calibrated TXD EEPROM range `focus_absolute: min=360 max=605 step=1 default=360` and completed a full six-step sweep (`360 → 420 → 480 → 540 → 605 → 480`) with exact readback and zero I²C errors.
- **Rear Flash LED (`/sys/class/leds/white:flash`, `c400000.spmi:pmic@2:led-controller@ee00`)**: Enabled with `led-sources = <2>, <3>` (1-based matching stock `qcom,id` 1 & 2) and conservative board limits (`led-max-microamp = 300000` = 300 mA total torch, `flash-max-microamp = 1000000` = 1000 mA total flash, `flash-max-timeout-us = 1280000`). Setting torch brightness `64` and `128` succeeded with empty `flash_fault` (zero open-circuit, short-circuit, or over-current faults), and even with the tablet lying face-down on a desk, `hi1339` captured a measurable green-channel mean rise (`0.00 → 0.37`, max `0 → 18`) while torch was active.
- **Remaining Owner Acceptance**: Handheld optical sharpness / autofocus convergence on a lit subject and direct visual confirmation of rear flash LED illumination off the desk.

## Next flash change (historical design checklist)

1. Obtain the CN350 flash driver or board electrical limits and the matching HAL flash policy. Use those inputs to establish one ganged LED's allowed total torch and flash currents, timeout, and behavior at the board's thermal and battery limits. The DTB supplies the channel crosswalk and timeout, but does not establish those operating currents. Until resolved, leave the node disabled. No standalone DTS candidate was created.
2. Once those limits have been established, add a single board LED child and link HI1339 with `flash-leds`. Run `dtbs_check` against the PMIC and sensor bindings, including a binding for the board sensor if required. Confirm a flash media entity and enumerate its controls before firing it in an attended trial. Validate torch, strobe and fault handling within the verified limits, then check whether libcamera and qcam expose a control. Establish shared flash ownership before advertising the flash on the macro camera.
